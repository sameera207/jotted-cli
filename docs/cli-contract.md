# Building on Jotted: the CLI contract

This is the reference for anything built on top of Jotted: the desktop app, MCP connectors, agents, scripts. If you are an agent asked to build one of these, read this first.

**The rule:** a wrapper only runs `jotted …` with `--json` and reads what it prints. It never imports Jotted's Python, reads its SQLite database, edits `config.toml`, calls the local HTTP API, or types into a prompt. If you need something you can't get that way, the CLI is missing a command: ask for one rather than working around it.

- Exact arguments and data shapes for every command: [`docs/schema.json`](schema.json), the same as `jotted --json schema` prints. Both are regenerated from the code.
- Why the contract looks like this, and what's planned: [`specs/CLI-contract-spec.md`](../specs/CLI-contract-spec.md).
- The command reference below (between the GENERATED markers) is regenerated by `scripts/contract_docs.py`; edit the code, not those parts.

## Output

With `--json`, stdout carries exactly one JSON document, the envelope, and nothing else:

```json
{"v": 1, "ok": true, "data": {"id": 12, "text": "Book the retro room", "status": "open"}}
```

```json
{"v": 1, "ok": false, "error": {"code": "busy", "message": "The library is busy with another job; try again in a moment", "retry": true}}
```

- `v` is the contract version. Check it, or better, check `jotted --json version` once at start-up (see Versions).
- `data` is the command's result: an object or a list, shaped as `schema.json` says.
- `error.code` is for your code: branch on it, never on `message`.
- `error.message` is written for a person. Show it as it is.
- `error.retry: true` (with `busy`) means try the same thing again shortly.
- `error.step` (with `not_set_up`) names the setup step that is missing.
- Logs go to stderr. Ignore stderr, or show it in a debug view.
- `--json` can come before or after the command: `jotted --json items` and `jotted items --json` are the same.
- `events --follow` is the one exception to "one document": it prints one JSON object per line (see Live updates).

Without `--json`, output is for people and can change at any time. Never parse it.

### Error codes and exit statuses

The exit status follows the code, so a shell script can branch without parsing JSON.

Treat a code you don't know as a failure and show its message: new codes can be added within a contract version.

### Values

- IDs are stable: an item keeps its `id` for life.
- An item's `status` is `open` or `done` on the list. Two more show up only when you ask for them (`items --status proposed|dismissed|any`, `items get`) or in their events: `proposed` (an agent found it; it waits for the person to accept it, and never reaches the tablet before) and `dismissed` (kept so its source never adds it again).
- An item's `origin` is the source plugin's name (read from handwriting), `todo` (written in a row of the To-do document), `web` (typed in an app or the CLI) or `agent` (added by an agent). New origins can appear.
- An item's `source` says where it came from. `doc_id`, `name`, `folder`, `page` and `anchor` are the handwritten page (and are empty or 0 for a typed item). `kind`, `key`, `title`, `url` and `excerpt` describe any source: a `gdoc` line, a `gmail` message, a `jira` ticket. `(kind, key)` is unique, which is how an agent's item is added only once. `page` is the page to draw (`image page`), or null when there is no handwriting. Show `excerpt`, `title` and `url` as plain text: an agent copied them from another document. Never open `url` on its own.
- Paths are the device's own: `/Meeting Notes/Weekly sync`.
- Times are ISO 8601 in UTC. Event times (`at`) look like `2026-10-03T04:12:09Z`; some older fields (an item's `created_at`, `published_at`) still carry microseconds and `+00:00`. Parse with a full ISO 8601 parser.
- Fields are only ever added within a contract version. Ignore fields you don't know.

## Prompts and secrets

Jotted asks a question only when stdin is a terminal **and** `--json` is off. Under `--json`, or with stdin closed, a command that would need an answer fails at once with `usage` and says which flag to use. It never waits.

Secrets and one-time codes go on stdin:

```bash
printf '%s\n' "$KEY"  | jotted --json ai key llm --stdin
printf '%s\n' "$CODE" | jotted --json connect --stdin
```

Never put a secret on the command line, where other processes can see it.

`jotted start` and plain `jotted setup` are interactive walkthroughs for people. Wrappers use the steps below instead.

## Setting up

Setup is a list of steps. Each step says whether it is done and names the command that completes it, so a wrapper can walk setup without knowing the steps in advance:

```bash
jotted --json setup status
```

```json
{"v": 1, "ok": true, "data": {"complete": false, "steps": [
  {"id": "app_folder", "title": "A home for settings and data", "done": true, "detail": "/Users/sam/Library/Application Support/jotted"},
  {"id": "remarkable.rmapi", "title": "rmapi, to reach the reMarkable cloud", "done": true, "detail": "rmapi v0.0.35, checksum verified"},
  {"id": "remarkable.connect", "title": "Your reMarkable", "done": false, "command": "connect --stdin"},
  {"id": "llm", "title": "The language model's key", "done": false, "provider": "anthropic", "command": "ai key llm --stdin"},
  {"id": "jev", "title": "The Jev plugin", "done": false, "optional": true, "command": "ai key jev --stdin"},
  {"id": "folders", "title": "A watched folder", "done": false, "command": "watch add PATH"}
]}}
```

The flow for a setup screen:

1. Run `setup status`. If `complete` is true, setup is done.
2. Run `setup prepare` once. It does every step that needs no answer from the person: it creates the app folder and downloads rmapi (checksum checked). It's safe to run again.
3. For each step that isn't done, show a screen and run its `command` with what the person gives you (on stdin when it ends in `--stdin`). Steps with `optional: true` can be skipped.
4. Run `setup status` again to confirm.

Steps from a source plugin are prefixed with its name (`remarkable.connect`). Don't hard-code the list: another plugin brings other steps. `connect` refuses to replace an existing connection with `conflict` unless you pass `--replace`; a failed `--replace` keeps the old connection.

Any other command run before setup is complete fails with `not_set_up` and `error.step` set. Send the person to that step.

## Live updates

```bash
jotted --json events --follow
```

This prints one JSON object per line, one per change, as changes happen, whichever process made them (`jotted serve`, another CLI command, an MCP call):

```json
{"v": 1, "cursor": 1842, "at": "2026-10-03T04:12:09Z", "type": "item.added", "item": {"id": 12, "text": "Book the retro room", "status": "open"}}
{"v": 1, "cursor": 1843, "at": "2026-10-03T04:12:10Z", "type": "check.finished", "new": 2, "updated": 0, "missing": 0, "pages_read": 3, "errors": 0}
```

| `type` | Extra fields |
| --- | --- |
| `item.added` | `item`: the item as `items` lists it |
| `item.changed` | `item`: the item now (edited, done, reopened, moved, from the app or a tick on the tablet) |
| `item.removed` | `item`: `{"id": …}` only (dismissed, deleted, or no longer an action) |
| `item.proposed` | `item`: a proposed item, new or reworded. It isn't on the list (`items`) yet |
| `item.accepted` | `item`: a proposed item the person accepted. An `item.added` for it follows, so a screen that shows the list can ignore this one |
| `check.started` | none |
| `check.finished` | `new`, `updated`, `missing`, `pages_read`, `errors` |
| `todo.published` | `items`: rows on the To-do document |
| `settings.changed` | `settings`: all settings now |
| `source.error` | `message`: for a person |

- Keep the last `cursor` you saw. After a restart, pass it back: `events --follow --since CURSOR`, and you miss nothing.
- Without `--since`, `--follow` starts from now.
- `events --since CURSOR` without `--follow` returns one envelope: `{"cursor": …, "events": […]}`. Without either, it returns the last few events.
- Events are kept for a week. If your cursor is older, reload the whole list (`items --status all`) and carry on from the latest cursor.
- Ignore event types you don't know.

## Speed: `jotted serve`

Each `jotted` run starts Python, which takes a fraction of a second, plus more for commands that load the model SDK. For an app, keep `jotted serve --no-browser --port 0` running. While it runs, CLI commands hand their work to it and come back faster, with exactly the same output, errors and exit codes. You don't have to do anything differently.

- `--port 0` picks a free port. You never need the port: keep using `jotted` commands.
- `--local` forces a command to run in its own process.
- Stop the server with SIGTERM; it cleans up after itself.
- The HTTP API it serves is internal. Don't call it.

## Versions

```bash
jotted --json version
```

```json
{"v": 1, "ok": true, "data": {"version": "0.4.0", "contract": 1, "contract_min": 1, "source_plugin": "remarkable", "python": "3.11.15", "bundled": false}}
```

- `version` is the release (semver for the product).
- `contract` is the contract version, the `v` in every output. It changes only when a wrapper would break: a removed or renamed command, option or field, or a changed meaning. Adding a command, option, field, event type or error code doesn't change it.
- `contract_min` is the oldest contract this build still accepts.
- At start-up, if `contract` isn't one you were built for, stop and say this version of Jotted needs updating, instead of half-working.
- Pin a release. Its `schema.json` is attached to the GitHub release and kept in `docs/schema.json` at that tag.
- To bundle Jotted in an app, use the release's standalone build: `jotted-X.Y.Z-macos-arm64.tar.gz` and `-macos-x64.tar.gz`, each with a `.sha256` beside it. Each unpacks to a `jotted/` folder holding the `jotted` executable and `_internal/` (Python and every library inside; nothing to install). Run `jotted/jotted` from where it is unpacked: it needs its `_internal/` folder beside it. Sign every file in the folder with your app.
- A copy bundled inside an app should run with `JOTTED_BUNDLED=1`: then it never updates itself (`update` fails with `conflict`), and the app updates it by shipping a new pin. A standalone build counts as bundled even without it.

Other environment variables: `JOTTED_CONFIG` (another `config.toml`), `JOTTED_HOME` (another app folder; handy for tests), `JOTTED_NO_UPDATE=1`, `JOTTED_CLAUDE_CONFIG` (the Claude Desktop settings file `claude connect` edits; for tests).

## Recipes

### A screen in an app

1. Find the command in the reference below. Read its `data` shape in `schema.json`.
2. Run it with `--json`, then check `ok`.
3. On failure, branch on `error.code`: `not_set_up` goes to setup, `busy` retries after a moment, `not_connected` shows a "reconnect" action (`connect --stdin --replace`), `model_error` shows a "check your key" action. Anything else shows `error.message`.
4. To refresh, listen to `events --follow` rather than polling.

For example, the To-do window runs `items` and `items done ID`. "Where it came from" runs `image page DOC PAGE --highlight A --width 600` with the item's `page` fields (without `-o`, the SVG comes back in `data.svg`). Notebooks run `library` and `watch`. Settings runs `settings`, `settings set KEY VALUE`, `ai`, `ai model NAME`.

### Proposals: items an agent found

An agent that reads other documents (a meeting doc, mail, a ticket) proposes what it found instead of adding it:

```bash
echo '[{"text": "Send Dana the estimate", "source": {"kind": "gdoc", "key": "1AbC#h.x7q", "title": "Platform sync", "excerpt": "Sam to send the estimate to Dana"}}]' \
  | jotted --json items add-batch --stdin --propose --agent
```

1. Each item gets an outcome: `created`, `existing` (that source key was added before), `dismissed` (the person turned it down before: nothing is added), or `invalid`/`conflict` with its `error`. One bad item doesn't stop the others.
2. Proposed items wait: show them with `items --status proposed` and let the person accept (`items accept ID…`, or `items accept --all`) or dismiss (`items dismiss ID`) each one. Accepted items reach the To-do document on its next update.
3. At most `proposed_limit` (setting, 200) wait at once; past that, proposing fails with `conflict`.
4. `items add TEXT --source-kind K --source-key KEY` adds one item the same way: once per key, with `created` false when it was there already.

`status` counts proposed items (`items.proposed`), for a badge.

### An MCP connector

`jotted mcp` is already an MCP server on stdio. For Claude Desktop, `jotted claude connect` sets it up (a desktop app passes its bundled binary with `--command PATH`); `claude status` says whether Claude Desktop is installed (`installed`), whether it is connected, and whether that binary still exists, and `claude disconnect` removes it. Each backs up Claude Desktop's settings first and changes only the `jotted` entry. Claude Desktop starts `jotted mcp` without your environment, so `connect` writes `JOTTED_CONFIG`, `JOTTED_HOME` and `JOTTED_BUNDLED` into the entry's `env` when they are set; an app that bundles `jotted` runs `connect` with them as it runs its own copy. Any other client:

```json
{"mcpServers": {"jotted": {"command": "/absolute/path/to/jotted", "args": ["mcp"]}}}
```

Each tool runs one CLI command and returns its `data` as JSON text, or its `error` with `isError: true`. Item results carry text fields only (`id`, `text`, `status`, `owner`, `owner_name`, `origin`, `source`, `page`), never images. `items_list` returns `{"items": […], "next_cursor": …}`, 50 at a time. Items the agent adds are `origin: agent`. `items_add` is for what the person asked for and is added straight away (proposed instead under the setting `mcp_add_mode: propose_all`). `items_propose` is for what the agent inferred, and always waits for the person. Hosts that render MCP Apps (Claude Desktop) get the Jotted widget too: `show_list` opens `ui://jotted/list`, and the tools marked "for the widget only" below are offered only to a host that advertises the `io.modelcontextprotocol/ui` extension, so handwriting images never reach a model. Tools that change what Jotted reads are offered only by `jotted mcp --admin`:

Building your own connector (another protocol, a remote bridge)? Do the same thing: map each tool to a `jotted --json …` command, take its input schema from that command's arguments in `schema.json`, and return `data` or `error`. Never pass keys or one-time codes through an agent: when `setup_status` shows a missing key, tell the person which command to run.

To add a tool to `jotted mcp` itself, add a line to `TOOLS` in `src/jotted/mcp.py`; the input schema comes from the command.

### An agent with a shell

No MCP needed: tell it to run `jotted --json …`, read `docs/schema.json` (or `jotted --json schema`) for the commands, and branch on `error.code`.

## In another repo

For an app or connector in its own repo (like `jotted-desktop`), pin a Jotted release and keep its contract next to your code: download `schema.json` and `cli-contract.md` from that release's assets on GitHub (`gh release download vX.Y.Z -R sameera207/jotted-cli -p schema.json -p cli-contract.md`). Then put this in that repo's `CLAUDE.md` or `AGENTS.md`:

```markdown
## Jotted

This project talks to Jotted only through the `jotted` CLI, pinned to release vX.Y.Z.
Read `vendor/jotted/cli-contract.md` (how to use it) and `vendor/jotted/schema.json`
(every command, its arguments and the shape of its data) before writing code that calls it.
Run `jotted --json …`, check `ok`, branch on `error.code`. Never import Jotted's Python,
read its database, call its HTTP API, or pass keys through an agent. If a command you need
is missing, say so instead of working around it.
```

When you bump the pin, download both files again: the release notes list contract changes.
